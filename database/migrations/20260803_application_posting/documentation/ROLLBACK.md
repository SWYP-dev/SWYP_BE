# ApplicationPosting 마이그레이션 롤백

## 기본 원칙

이 마이그레이션은 MySQL DDL을 포함하므로 전체 작업이 하나의 트랜잭션으로 롤백되지 않는다. 부분 적용 상태에서 역방향 SQL을 임의로 실행하지 않고, 마이그레이션 직전에 생성한 DB 스냅샷 복원을 기본 롤백 방법으로 사용한다.

Phase 3부터 `kanban_cards.application_posting_id`와 `documents.application_posting_id`가 `NOT NULL`이 된다. 따라서 Phase 4 실행 전이라도 구버전 애플리케이션만 다시 배포하는 방식으로는 안전하게 롤백할 수 없다.

## Phase 1~3 실행 중 실패

1. 애플리케이션 중지 상태를 유지한다.
2. 실패한 SQL을 임의로 재실행하거나 `schema_migrations` 행만 삭제하지 않는다.
3. 실행 직전 DB 스냅샷으로 복원한다.
4. 구버전 애플리케이션을 기동해 정상 동작을 확인한다.
5. 실패 원인을 수정하고 처음부터 다시 적용한다.

## 새 애플리케이션 배포 후 롤백

배포 후 신규 데이터가 기록되지 않았다면 애플리케이션을 중지하고 DB 스냅샷을 복원한 뒤 구버전을 배포한다.

신규 데이터가 이미 기록됐다면 스냅샷 복원 시 해당 데이터가 유실될 수 있다. 이 경우 단순 롤백하지 않고 신규 데이터를 보존하는 별도 변환 절차를 작성하거나 문제를 전진 수정한다.

## Phase 4 실행 후 롤백

Phase 4는 `kanban_cards.job_posting_id`와 `documents.job_posting_id`를 제거한다. 실행 후에는 DB 스냅샷 없이는 구버전 구조로 복구할 수 없으므로, 새 버전의 운영 안정성이 확인되고 롤백 대기 기간이 끝난 뒤에만 실행한다.
